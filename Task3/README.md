# Стратегия защиты данных в рамках всей системы

## 1. Классы данных и необходимость защиты
- Идентификационные данные пациента (PII)
  - состав: ФИО, дата рождения, пол, паспорт/полис, СНИЛС, адрес, контактные данные
  - чувствительность: высокая
  - риски: кража личности, мошенничество, штрафы регулятора
  - состояния:
    - at rest: БД Patient Identity, CRM, договоры, сканы
    - in transit: формы портала, обмен между сервисами, уведомления
- Медицинские данные (PHI / EMR)
  - состав: диагнозы, жалобы, назначения, результаты анализов, выписки
  - чувствительность: очень высокая
  - риски: серьёзный ущерб репутации пациента, сильные санкции
  - состояния:
    - at rest: БД EMR, хранилище сканов анализов
    - in transit: между порталом и EMR, с лабораторией, между филиалами
- Финансовые данные
  - состав: сведения о платежах, чеки, суммы, статусы оплат, реквизиты
  - чувствительность: высокая (финансовая/коммерческая тайна)
  - состояния:
    - at rest: 1С, Payments Service, отчёты
    - in transit: между ККМ и 1С, между порталом и платежным шлюзом
- Операционные данные без ПДн
  - состав: справочники услуг, расписание без привязки к ФИО, агрегированные метрики
  - чувствительность: средняя/низкая
  - состояния:
    - at rest: отдельные таблицы, кэши;
    - in transit: API без PII.
- Аналитические данные
  - состав: агрегированные показатели, обезличенные выборки, синтетические датасеты
  - чувствительность: низкая, если PII/связка с личностью удалены
  - состояния:
    - at rest: Anonymized Store
    - in transit: выгрузки в BI/ML
- Логи и аудит
  - состав: журналы доступа к EMR/CRM, техлоги
  - чувствительность: средняя/высокая (часто содержат идентификаторы пациентов/пользователей)
  - состояния:
    - at rest: системы логирования
    - in transit: доставка логов в централизованное хранилище

## 3. Инструменты защиты
- Базовые инструменты (минимум, который должен быть)
  - шифрование дисков/томов серверов (Windows Server, БД‑серверы, файловый сервер) — BitLocker/LUKS, AES‑256
  - TLS 1.2+ для всех веб‑сервисов и API внутри и снаружи (портал, мобильное приложение, админские интерфейсы)
  - VPN для связи филиалов и удалённых сотрудников
  - RBAC для всех приложений, привязанный к ролям в AD/IdP
  - резервное копирование с шифрованием и контролем доступа к бэкапам
- Инструменты, которые нужно добавить (To‑Be)
  - шифрование БД на уровне сервера/тома для Patients Service, EMR, Payments, Audit Log
  - API Gateway с принудительным TLS, проверкой токенов, ограничением полей, rate limiting
  - Policy Engine + Data Tagging: политики доступа по тегам данных, а не только по таблицам
  - DLP‑решение (на почте/файловом шаре) для контроля утечек: запрет отправки файлов с PII наружу без шифрования
  - cистема централизованного логирования и patient‑privacy monitoring (аудит 100% обращений к медданным, автоматический поиск аномалий)
  - bнструменты управления ключами (KMS или HSM, либо их аналог в инфраструктуре): безопасное хранение ключей шифрования БД и TLS‑сертификатов

# 4. Автоматизированный контроль
- Мониторинг шифрования: проверки, что все критичные сервисы работают только по TLS, нет открытых HTTP/старых протоколов
- Автоматический аудит доступа к EMR/PII с ML‑или правил‑базированным поиском аномалий (подходы patient privacy monitoring)
- Автопроверки CI/CD:
  - запрещены новые API/таблицы с тегами conf.pii без шифрования и политик доступа
  - линтер схем/Swagger на предмет "не выдать PII наружу"
- Регулярные отчёты по статусу защиты (шифрование включено/выключено, TLS‑версии, использование VPN)
