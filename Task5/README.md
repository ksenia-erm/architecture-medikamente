# Cutover‑план миграции системы "Медикаменте"

## 1. Выбор стратегии миграции

### Анализ контекста

- Поскольку тематика проекта медицинская, критично важны непрерывность оказания услуг, доступность иконсистентность данных.
- Сейчас все работает на одном сервере, много ручных операций и Excel, нет чётких API.
- Новая архитектура — микросервисы (Java (или другой выбранный стек)/K8s/PostgreSQL), портал пациентов, интеграции с лабораторией, мобильное приложение.

Полноценный "quick win" невозможен: одновременный одномоментный переход слишком рискован для клиники.

### Выбранный подход: Parallel Run + элементы Branch by Abstraction

**Почему Parallel Run подходит:**
- Позволяет держать старую систему как "страховочную сетку", пока новая архитектура обкатывается на реальных данных.
- Можно постепенно переводить разных пользователей (например, сначала новый портал для части пациентов, затем подключать врачей).
- Риск простоя и потери бизнес‑функций ниже, чем при одномоментном отключении монолита.

**Ограничения и как их компенсировать:**
- Основная проблема Parallel Run — синхронизация данных и двойная запись.
- Для снижения этого риска используем элементы **Branch by Abstraction**: вводим слой абстракций/интеграционный слой поверх legacy (например, над Excel/1С), через который постепенно переведём операции на новую БД/сервисы, сохраняя единый вход для клиентов.

Итого: стратегия — **параллельный запуск старой и новой систем с поэтапным переносом функционала через абстракционный слой**, чётко описанный cutover‑план и понятный сценарий отката.

## 3. Ключевые риски и меры по управлению

### Основные риски Parallel Run
1. **Рассинхронизация данных между старой и новой системой**
    - Меры:
        - внедрение механизма двусторонней синхронизации/CDC (change data capture) через интеграционный слой
        - отчёты сравнения (сверка количества записей, сумм оплат, расписания)
        - ограничение периода полного Parallel Run по времени

2. **Рост сложности и нагрузки на команду (поддержка двух систем)**
    - Меры:
        - чёткий roadmap: какие домены и в какие даты переключаются
        - уменьшение параллельного окна (быстрая декомиссия устаревших участков после успешной проверки)
        - распределение ответственности и формальные "готовность‑пункты" перед каждый cutover‑шагом

3. **Сбои в процессе финального cutover**
    - Меры:
        - заранее подготовленный и проверенный план отката (что возвращаем и как, в какие сроки)
        - проведение тестового "dry‑run" cutover на стейджинге
        - выбор временного окна с минимальной нагрузкой (например, ночь/выходной)

4. **Неготовность пользователей работать в новой системе**
    - Меры:
        - обучение ключевых ролей (врачи, ресепшен, касса) до cutover
        - период "мягкого входа" — пользователи могут какое‑то время возвращаться к legacy, но официально фиксация идёт в новой системе
        - сбор обратной связи и быстрые UX‑исправления

## 4. Распределение ролей

- **Технический директор**
    - Выбор архитектурного подхода и стратегии миграции.
    - Утверждение доменной модели, cutover‑плана и критериев готовности.
    - Принятие решений "go/no‑go" по этапам.

- **Системный администратор / DevOps**
    - Развёртывание и поддержка новой инфраструктуры (K8s, БД, мониторинг).
    - Настройка сетей, VPN, DMZ, резервного копирования.
    - Участие в подготовке и исполнении cutover‑окна.

- **Бизнес‑аналитик**
    - Описание процессов, выявление "источников истины", сценариев миграции.
    - Участие в тестировании и приёмке (проверка бизнес‑логики, отчётности).

- **Разработчики**
    - Реализация новых микросервисов, интеграционного слоя, ETL.
    - Поддержка branch‑by‑abstraction логики (переключение между legacy и новой реализацией).

- **Представители бизнеса (руководители отделов)**
    - Приоритизация функций для миграции.
    - Участие в UAT и решении, когда можно отключать legacy по конкретным процессам.
