# Движок классификации данных
## Краткое описание идеи
Перед загрузкой в аналитическое хранилище данные проходят через `Data Classification Layer` - отдельный контейнер/сервис в аналитическом контуре. 
Функции сервиса:
- принимает сырые батчи (выгрузки из EMR/CRM/1С, файловые парсеры, другие сервисы, работающие с данными)
- анализирует схему и содержимое
- присваивает полям теги конфиденциальности и назначения (например, `conf.pii`, `conf.health`, `finance.payment`, `use.analytics`, etc)
- решает, в какой слой хранилища и в какой форме поле можно сохранять (как есть / псевдонимизировать / агрегировать / отбрасывать)

# Схема работы
- ERM, CRM, 1с и другие сервисы, работающие с данными, отдают батчи данных во входной ETL data-ingestion-service
- он входящие данные приводит к единому формату 
- перед сохранение данных в сырое хранилище (Secure Raw Data Lake) вызвает `Data Classification Layer`
- `Data Classification Layer` имеет внутри ряд слоев для обработки данных
  - Schema Analyzer - извлекает поля, типы, структуру, сравнивает с информацией из Metadata Service, если новые поля — помечает как "unknown" и запускает дополнительные проверки
  - Rules Engine - правило‑база/политики (по именам полей, паттернам, источнику, семантике)
    - по названию/типу/контексту (email, phone, snils, address, diagnosis_code) определяет предполагаемый класс
    - учитывает источник (EMR → кандидаты в `conf.health`, CRM → `pii.identity`/`pii.contact`, Payments → `finance.payment`), правила конфиденциальности
  - Content Scanner 
    - поиск PII/PHI по шаблонам (телефон, e‑mail, паспорт, СНИЛС и т.п.)
    - проверяет подозрительные поля по регуляркам/ML‑модели
  - Tagging Module - формирует набор тегов для каждого поля/колонки и сохраняет в Metadata Service
  - Transformation Module - по политике решает: оставить, замаскировать, псевдонимизировать, агрегировать или удалить
    - `conf.health` + `use.analytics` → псевдонимизация идентификатора пациента, хранение только кодов диагнозов и возрастных групп
    - `conf.pii` в аналитическом слое → удалить/замаскировать
    - всё с `use.operational_only` → не пропускать дальше в Analytics Layer
- При этом `Data Classification Layer` через интеграцию с сервисами из Data Management Layer получает необходимые классификаторы, политики и правила обработки данных
- Для экономии времени классификаторы и политики могут храниться в кэше сервиса с регулярной инвалидацией

# Метрики эффективности классификации
Что измерять, чтобы понимать, насколько движок работает хорошо и как его оптимизировать:
- Coverage (покрытие тегами)
  - доля колонок в хранилище, у которых присвоен хотя бы один тег конфиденциальности/назначения
  - цель: близко к 100% для доменно значимых таблиц
- Accuracy / Precision / Recall (по размеченному "золотому" датасету)
  - Доля верно классифицированных PII/PHI среди найденных (precision)
  - Доля фактических PII/PHI, которые были обнаружены (recall)
  - Источник: периодическая ручная разметка подмножества данных
- False Positive Rate
  - Сколько полей помечены как конфиденциальные без реальной необходимости
  - Важна балансировка: низкий FPR, чтобы не превращать аналитический контур в избыточно ограниченный
- Latency классификации
  - Время обработки батча/объёма N записей Classification Engine
  - Важно для SLA nightly/batch загрузок при росте объёмов
- Процент инцидентов, связанных с неправильной классификацией (должен стремиться к нулю)
  - количество багов/инцидентов, где причина — неверная метка, за период

Эти метрики позволят видеть, где надо дообучать правила/ML, усиливать паттерны или менять архитектуру (например, выносить Content Scanner в отдельный масштабируемый сервис).

# Масштабируемость системы
- Горизонтальное масштабирование классификатора
  - Data Classification Engine — stateless‑сервисы в Kubernetes, масштабируются по CPU/очередям
  - Content Scanner можно вынести в отдельный worker‑кластер
- Разделение по доменам/типам источников
  - отдельные пайплайны и worker‑группы для EMR, CRM, Payments, логов
  - это позволяет масштабировать "тяжёлые" направления (например, медданные) отдельно от остальных
- Слоистое хранилище
  - Raw/Anonymized могут находиться в масштабируемом объектном хранилище (S3) + колоночная БД для Analytics
  - при росте нагрузки добавляются ноды хранилища/вычислительные ресурсы
- Кэширование метаданных
  - Data Catalog держит горячие схемы/теги в кэше, чтобы не бить в БД на каждый запрос классификатора
- Поэтапное расширение
  - сначала классифицируются критичные домены (медкарта, PII, платежи)
  - постепенно подключаются менее критичные источники (операционная статистика, логи)
